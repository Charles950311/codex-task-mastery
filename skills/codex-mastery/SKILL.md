# Codex Mastery（任务总控）

目标：让 Codex **先对齐目的，再高效执行，最后用证据交付**。

## 何时使用
- 请求模糊、目标或验收标准不明，或你正要“猜着做”。
- 任务跨多步骤、多文件、跨会话。
- 用户要求省时间 / 省 token、减少返工、提高完成质量。
- 用户要求生成或优化提示词、skill、AGENTS.md。
- 用户以「开始工作」+ 任务诉求发起 → 先走 `start-work`，把诉求改写成可执行提示词。

## 路由表
| 情况 | 调用 |
|---|---|
| 用户说「开始工作」+ 任务诉求 | `start-work`（诉求 → 可执行提示词） |
| 目标 / 范围 / 验收标准不清 | `task-brief` |
| 用户给了粗糙想法，要生成或优化提示词 | `prompt-forge` |
| 长任务、上下文变重、想省 token | `context-budget` |
| 要动手实现，需拆成小步 | `plan-slices` |
| 要写新功能 / 工具 / 依赖 | `repo-first` |
| 要交付、声称完成、或高风险决策 | `verify-claim` |
| 简单明确、单步、低风险 | 直接做，不要过度流程化 |

> 简单任务直接执行。只有上述条件成立时才加载对应技能——这本身就是 `context-budget` 的要求。
>
> 本路由只分发“流程 / 元技能”。领域内容技能（如 `lottery-number-analysis`：双色球 / 大乐透选号数学参数化复现；`lotto-number-pick`：大乐透专例）不在本路由表内，由用户显式点名或按各自 `description` 触发加载。

## 五条不可协商的行为（全程适用）
1. **暴露假设**：非平凡任务开工前，用 3 行以内写出你的假设，并说“无异议我就按此执行”。
2. **不猜**：遇到冲突或缺口，先停下说清楚，再问最小必要的问题；只有真正阻塞才打断用户。
3. **该反对就反对**：不做 yes 机器。指出具体代价（尽量量化），给替代方案；用户知情后可覆盖。
4. **复杂度最小化**：能用 50 行就不用 200 行；新抽象必须证明其价值。
5. **范围纪律**：只改与任务相关的部分，不做“顺手重构”。

## Token 与时间纪律（常驻）
- 先定位再读取：用 `rg` / 目录列表锁定文件，不整文件乱读。
- 一次批量发起相互独立的工具调用。
- 修改后不重复读取同一文件；引用路径而不是粘贴大段内容。
- 详情放 `references/`，按需加载（渐进披露）。
- 回复默认精简；用户要“长 / 短版本”时给出 25/50/75/100% 深度选项。
- 上下文到约 75% 主动压缩；在阶段边界压缩，不在实现中途压缩。

## 完成判定（停止条件）
- 验收标准逐条有证据；没有证据就不说“完成”。
- 无未决阻塞、无被跳过的验证；有验证缺口就显式说明。
- 交付信息：改了什么、为什么、证据、剩余风险 / 下一步。

## 迷你案例
输入：「Codex 老是把我的重构顺手改乱，怎么办」。
路由判断：这是行为纪律诉求，用户在问方法、不是下任务 → 不开工、不澄清、不拆片；直接给 `verify-claim` 的红线，并建议把「范围纪律」固化进 AGENTS.md。
错误示范：把它当开发任务走一遍澄清与规划流程，徒增往返。
对照：简单单步请求（「把这个错别字改了」）→ 直接做，不加载任何技能。
