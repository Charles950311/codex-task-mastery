# Verify Claim（证据化验证）

原则：**自信 ≠ 正确。没有新鲜证据，就不说“完成”。**

## 何时使用
- 要声称“做完了 / 修好了 / 通过了 / 安全”。
- 非平凡决策：引入或修改分支逻辑、跨模块 / 服务边界、类型系统无法验证的属性（线程安全、幂等、顺序、不变量）、不可逆副作用。
- 不熟悉的代码、高风险改动（生产、认证、迁移、不可逆操作）。

**不用时**：机械操作（改名 / 格式化 / 移动文件）、明确无歧义的一行改动、纯工具操作。若对每个按键都怀疑，就什么都交付不了。

## A. 完成前验证循环
1. **定义声明与成功标准**：你到底在断言什么？成功判据是什么？
2. **跑最小验证**：能证明它的最小测试 / 检查 / 构建 / 冒烟。
3. **读实际输出**：以真实输出为准，不用“应该没问题”。
4. **带证据汇报**：命令 / 结果 / 差异；失败就迭代；无法验证就说明原因与替代检查。
5. 验证通过前，**不得**使用“完成 / 已修复 / 通过”等措辞。

优先做**针对性验证**（先测改动路径），再逐步扩大到类型检查 / lint / 构建 / 冒烟。

## B. 非平凡决策的怀疑循环
```
- [ ] 1 CLAIM     — 写下断言 + 为什么重要
- [ ] 2 EXTRACT   — 抽出“产物 + 契约”，剥离你自己的推理
- [ ] 3 DOUBT     — 用对抗式、以“证伪”为目标的审查（最好换新上下文 / 子代理）
- [ ] 4 RECONCILE — 每条发现逐条对照产物文本判定
- [ ] 5 STOP      — 达到停止条件（只剩琐碎项 / 3 轮 / 用户明确要求提速）
```
无法获得“新上下文”时（例如身处子代理内），降级为自我质询并**标注为降级**，优先升级到主会话处理。

## 汇报模板
```
声明：<断言>
标准：<成功判据>
验证：<命令 / 检查 + 实际输出>
结论：通过 / 未通过 / 无法验证（原因 + 替代检查）
缺口与风险：<显式列出>
```

## 红线
- 用“应该”“看起来”“理论上”代替实际验证。
- 只测了无关路径就宣称完成。
- 失败后悄悄换判据（moving the goalposts）。
- 把“没跑的测试”“降级的检查”说成“已验证”。
