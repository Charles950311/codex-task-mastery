# Context Budget（上下文与 Token 预算）

前提：**上下文窗口大小 ≠ 注意力预算。** 聚焦的少量上下文，效果优于塞满的大量上下文。

## 何时使用
- 长会话、上下文变重、开始变慢或变贵。
- 用户要“省 token / 省时间 / 简洁 / 短版本”。
- 要连续处理多个大任务，需要主动管理上下文。
- 用户要控制回复长度。

## 读取纪律
- **先定位再读取**：用 `rg` / `rg --files` / 目录列表锁定目标，再做定点读取。
- **不整文件乱读**：大文件只取相关区段。
- **不重复读取**：改完文件不回头再读；工具失败即视为未生效。
- **引用路径，不粘贴大段内容**（回复用户时同理）。
- **外部资料按需加载**：只读 `SKILL.md` 直接指向、且当前任务需要的参考文件；不要顺着引用一路深挖。

## 调用纪律
- 相互独立的工具调用**合并到同一次**发起。
- 不做无收益的检索升级；问题已可回答就停止。
- 不要同时启用大量 MCP / 工具：工具描述本身占上下文。按需开启，用完关闭。

## 上下文纪律
- 只保留与本任务相关的信息；目标 <2,000 行聚焦上下文。
- 把**任务关键信息放在上下文末尾**（当前错误、当前约束、任务定义），不要埋进背景材料。
- 长会话主动清理：失败的尝试、被替换的草稿、冗长的工具输出。
- “上下文悬崖”：到约 75% 就开始压缩，不要等满。
- 记得：事实 / 记忆 / 历史输出是“未评审上下文”，不是策略；关键结论要回到权威来源核验后再用。

## 压缩（compaction）
- **该压**：研究 / 探索之后、里程碑之后、调试之后、放弃某方案之后。
- **不该压**：实现中途（会丢变量名、路径、半成品状态）。
- 只在阶段边界压缩；压缩前确保“任务定义”与“当前错误”被显式保留。
- 详见 `references/token-and-compaction.md`。

## 回复长度控制（用户要“控制长度”时）
先估计输入 tokens 与复杂度，给出 4 档让用户选：
```
输入 ~N tokens | 类型 X | 复杂度 Y
[1] 精简 25%  -> 直接结论，无铺垫
[2] 适中 50%  -> 结论 + 必要背景 + 1 例
[3] 详细 75%  -> 完整答案 + 备选方案
[4] 穷尽 100% -> 不限
```
- 若用户已给信号（“1 / 短版 / tldr / 详细 / 穷尽”），直接按档回答，不要反问。
- 用户一旦选定，本会话静默沿用（除非改档）。
- 用户没说时，默认保持精简。
