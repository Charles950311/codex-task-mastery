# 开始工作 · 工作流与输出模板

> 供 `start-work` 使用。按需裁剪：清晰任务走 Fast 模式，模糊任务走 Clarify 模式。

## 1. 工作流详解

### 步骤 1 — 接收与对齐
从诉求中提取四要素：
- **Goal（目标）**：一句可观察的结果。
- **Scope（范围）**：做什么 / 不做什么。
- **成功标准**：怎么算完成。
- **硬约束**：技术栈、兼容性、安全、时间、环境。
缺哪一项就在后面补。

### 步骤 2 — 暴露假设
```
理解：用户想 <可观察结果>，而不是 <字面请求>。
置信度：约 N% — 缺：<1-3 项关键信息>
```

### 步骤 3 — 补关键缺口
- 只在**真正阻塞**时提问；一次一个问题，并附上你的猜测 + 理由。
- 能在仓库 / 文档 / 上下文里查到的，先查再问。
- 非交互环境：把缺口标为「待确认」，不要猜。

### 步骤 4 — 改写提示词
套用骨架（来自 `prompt-forge`）：
```
【目标】一句可观察的结果
【背景】相关文件、约束、已有约定
【范围】要做 / 不做
【要求】技术栈、风格、边界条件
【完成标准】可验证的 Definition of Done（AC-1、AC-2…）
【输出格式】期望交付物形态
【验证】如何自证
```

### 步骤 5 — 交付与路由
推荐执行链：
- 跨多文件 / 有风险 → `plan-slices` -> `verify-claim`
- 要写新功能 / 工具 / 依赖 → 先 `repo-first`
- 长任务 / 上下文重 → `context-budget`
- 要交付 / 声称完成 → `verify-claim`

## 2. 三种模式
| 模式 | 触发 | 行为 |
|---|---|---|
| Fast | 诉求清晰、单步、低风险 | 直接改写，不提问 |
| Clarify | 缺 who / why / 成功标准 / 约束 | 先问最小问题，再改写 |
| Non-interactive | CI / 自动运行 | 不猜，缺口列为「待确认」交付 |

## 3. 输出模板
```
## 理解
<我的理解>。置信度约 N%。缺：<...>

## 优化提示词
（代码块，可直接粘贴）
【目标】...
【背景】...
【范围】...
【要求】...
【完成标准】...
【输出格式】...
【验证】...

## 诊断与改写理由
- 原诉求问题：<歧义 / 缺验收 / 范围过大 / 不可验证 / 缺上下文>
- 改写点：<逐条一句话理由>

## 推荐执行链
`<技能>` -> `<技能>`（理由一行）

## 下一步
可直接使用；回复「执行」我就按此推进。
```

## 4. 示例
原诉求：帮我弄个导出功能

改写：
```
【目标】实现「导出 CSV」，使已登录用户能把当前列表数据下载为文件。
【背景】技术栈 <...>；列表组件 <文件>；已有约定 <...>。
【范围】做：按钮 + 后端导出接口；不做：Excel/xlsx、定时导出、权限模型改动。
【要求】列固定为 [id, name, created_at]；空列表也导出表头；UTF-8。
【完成标准】AC-001 点击导出下载文件且列正确；AC-002 空列表导出仅表头；现有测试全绿。
【输出格式】前端按钮 + 接口代码 + 集成测试。
【验证】运行 <测试命令>，附输出。
```
诊断：原诉求无「导出什么 / 给谁 / 列格式 / 完成标准」——补范围与可验证 DoD。

## 5. 质量红线
- 无「完成标准」的提示词 = 不合格。
- 模糊词（正确 / 快 / 稳）必须换成可观察证据。
- 不执行任务（除非用户确认「执行」）。
