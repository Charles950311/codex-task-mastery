# Start Work（开始工作 · 任务诉求 → 可执行提示词）

触发：**「开始工作」**（同义：「开工 / start work / 按这个开始 / 按这个任务开工」）。

目标：把用户的**原始任务诉求**改写成 **Codex 能更好实施的结构化提示词**，并给出后续执行建议。

## 何时使用
- 用户以「开始工作」+ 一段任务诉求发起。
- 用户丢来一段粗糙描述，想要「能直接执行的高质量提示词」。

## 何时不用
- 用户只是闲聊或提问 → 直接回答。
- 诉求已足够清晰、单步、低风险 → 走 Fast 模式快速改写，不套澄清流程。

## 工作流（5 步，详细说明见 references/workflow-and-output.md）
1. **接收与对齐** — 锁定 goal / scope / 成功标准 / 硬约束四要素。
2. **暴露假设** — 3 行内写出「我的理解 + 置信度 + 还缺什么」。
3. **补关键缺口** — 只在真正阻塞时，一次问一个问题（附猜测）；非交互环境列为待确认项。
4. **改写提示词** — 套用结构化骨架，产出可验证的 Codex 提示词。
5. **交付与路由** — 输出提示词 + 诊断 + 推荐执行链 + 确认句。

## 输出契约（顺序固定）
1. **理解** — 我的理解 + 置信度（低于 70% 时必须写清缺什么）。
2. **结构化提示词**（代码块）— 【目标】【背景】【范围】【要求】【完成标准】【输出格式】【验证】。
3. **诊断 / 改写理由** — 原诉求的问题 + 每处改写一句话原因。
4. **推荐执行链** — 如 `plan-slices` -> `verify-claim`；写新东西先 `repo-first`。
5. **确认句** — 「可直接使用；回复『执行』我就按此推进。」

## 行为红线
- 本技能产出的是**提示词**，默认不直接执行任务；执行需用户确认。
- 不编造上下文；未知信息写 `TODO / 待确认`。
- 不为凑格式扩大范围；保持用户原意，只做补全与结构化。
- 诉求已足够清晰时跳过澄清直接改写（这本身是 `context-budget` 的要求）。

## 与其它技能的关系
- 澄清意图复用 `task-brief` 要领；提示词骨架复用 `prompt-forge`。
- 改写后要落地：`plan-slices` 拆步 -> `verify-claim` 收口；写新东西先 `repo-first`。
- 长任务用 `context-budget` 控开销；总控入口仍是 `codex-mastery`。
