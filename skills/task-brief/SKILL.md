# Task Brief（意图澄清与目标锁定）

核心：**在写第一行代码、出第一个计划之前，先锁定“要达成什么、怎么算达成”。** 大多数返工来自把模糊需求当成明确需求。

## 何时使用
- 请求缺少 **who / why / success / constraint** 中至少一项。
- 请求是“惯例式”的（“做个后台”“弄快点”），不问就只能靠猜。
- 你发现自己准备用未验证的假设往下做。
- 用户明确说：“先问清楚”“别瞎猜”“我们确定吗”。

**不用时**：明确且自足的小任务（改名、修错别字、跑个命令）、纯信息查询、机械操作。优先用最快路径，不要为流程而流程。

## 流程

### 1. 先立假设，带置信度
用一句写下你当前对目标的理解 + 0-100% 置信度 + 还缺什么：
```
假设：用户其实想要 <可观察的结果>，而不是 <字面请求>。
置信度：约 30% — 缺：给谁用、成功标准、硬约束
```
置信度低于 70% 时，必须补上“还缺什么”，让用户知道这次澄清要解决什么。

### 2. 澄清：一次只问一个，且附上你的猜测
```
Q: <一个聚焦问题>
猜测: <你的假设 + 推出它的理由>
```
- 一次一个：用户才能对你的猜测作反应；批量提问会诱发敷衍回答，且后面的问题依赖前面的答案。
- 带猜测：用户否定一个错误猜测，比从零构造答案快得多，也让你的假设显性化。
- 只问**真正阻塞**的问题；能在仓库 / 文档里查到的，先查再问。
- 交互不可用时（CI / 自动运行 / 非交互）：不要猜，把缺口标为阻塞项交付。

### 3. 产出简报
按 `references/acceptance-brief.md` 模板产出。最小可用版本包含：
- **Goal**：一句可观察的结果句（是结果，不是实现选择）。
- **Scope**：in / out（明确列出“不做什么”）。
- **Context**：已发现事实（可从仓库 / 产物验证的现状与约定）；业务约束（只能由用户或 PRD / 合同 / 政策提供，**绝不从代码推断**）；假设（待确认）。
- **Acceptance Criteria**：每条 = 场景 + 触发 + 可观察预期 + 禁止项 + 验证方式 + 优先级。
- **Verification Plan**：每条标准对应的验证证据与状态。
- **Blocking Decisions**：只列真正影响正确性 / 安全性的待决项，不是偏好项。

### 4. 不默认阻塞
需求已足够清晰时，记录假设与验收标准后**直接继续**（或交接给 `plan-slices`），不要为了走流程而卡住。

## 质量红线
- “正确”“安全”“快”“稳定”这类词，必须换成可观察证据，或明确标注为人工判断。
- 业务规则不得伪装成“从代码发现的事实”。
- 每条必需标准都要有验证方法。
- 反问控制在最少必要；把短小相关的问题合并成一次问。

## 交接
把验收标准 ID（AC-001…）交给 `plan-slices` / `verify-claim`，作为实现与验证的锚点。
